\begin{abstract}
This report studies whether explicit multi-agent workflows can improve large language model reasoning on MATH-500 and HumanEval compared with direct and chain-of-thought prompting. I design task-specific workflows that convert one-shot generation into candidate diversification, selection, and targeted repair. For MATH, the workflow samples independent reasoning paths, selects the most self-consistent answer, and canonicalizes the final boxed output. For HumanEval, the workflow combines code candidate diversity with public-test execution and reflection-based repair. On the full MATH test split, the proposed \texttt{manual\_v1} workflow improves accuracy from 0.88889 with direct prompting and 0.89300 with CoT to 0.91770. On HumanEval, \texttt{manual\_v1} improves over direct prompting and a no-public-test ablation reaches the best score, showing that candidate diversity is a major source of gain.
\end{abstract}

\section{Introduction}

Large language model agents can improve reasoning by decomposing a task into multiple model calls, critiques, revisions, code execution steps, or ensemble decisions. AFlow formulates this idea as a search problem over code-represented agentic workflows, where reusable operators become nodes in a workflow graph and an optimizer searches for better graph structures \cite{zhang2025aflow}. Related work on multi-agent debate \cite{du2024debate} and optimizable agent graphs \cite{zhuge2024gptswarm} motivates comparing direct model calls against explicit multi-agent reasoning.

The assignment requires experiments on MATH-500 and HumanEval. MATH-style tasks test symbolic and quantitative reasoning \cite{hendrycks2021math}; HumanEval tests executable Python function synthesis \cite{chen2021humaneval}. These two datasets expose different failure modes. MATH answers often fail because a single reasoning chain makes an early algebraic or combinatorial mistake. HumanEval answers often fail because generated code has a small syntax, entry-point, or semantic error that can be detected by execution. The central design question is therefore how to spend additional model calls so that they correct likely task-specific errors rather than merely lengthen the same reasoning trace.

\section{Research Context}

The AFlow paper motivates the project by treating workflow design as an optimization problem over code-represented agent graphs \cite{zhang2025aflow}. In that formulation, LLM calls are nodes, edges encode execution logic, reusable operators provide common patterns such as ensemble or review-revise, and the optimizer searches over candidate workflow code using execution feedback. This assignment uses the same engineering abstraction but stops short of a full optimizer search because the available Kimi budget is the limiting resource.

The multi-agent debate paper provides a complementary design intuition: multiple model instances can maintain diverse candidate answers and revise after seeing other candidates \cite{du2024debate}. The manual workflows in this project use a lower-cost version of that idea. MATH \texttt{manual\_v1} creates independent solution candidates and selects among them, while HumanEval combines candidate diversity with executable public-test feedback. The ablations are designed to test whether the observed gains come from candidate diversity, execution feedback, or simply spending more tokens.

\section{Baselines}

I compare the proposed workflows against two base-model prompting strategies.

\paragraph{Direct baseline.} The direct math baseline asks Kimi K2.5 to solve the problem and place the final answer in \texttt{\textbackslash boxed\{\}}. The direct HumanEval baseline asks for valid Python code defining the required entry point.

\paragraph{CoT baseline.} The chain-of-thought baseline adds explicit step-by-step reasoning instructions. For HumanEval, the prompt allows analysis but asks the final answer to contain valid Python code, which the evaluator sanitizes before execution.

\section{Proposed Workflow Design}

The proposed workflows are manually designed multi-call agent graphs. They do not try to make every answer longer. Instead, they allocate extra calls to three targeted operations: \emph{diversify} the candidate set, \emph{select or repair} using task-specific signals, and \emph{standardize} the final output so the evaluator sees the intended answer.

\paragraph{MATH workflow.} A single MATH reasoning trace is brittle: if the model misreads a constraint or makes an early algebraic mistake, later steps often reinforce that wrong premise. The MATH \texttt{manual\_v1} workflow therefore generates three independent solution candidates under different reasoning instructions. One candidate emphasizes direct symbolic derivation, one emphasizes checking constraints and edge cases, and one emphasizes an alternative solution route. The workflow then extracts each candidate's final answer and uses a selection call to compare the candidate answers and their supporting arguments. The final cleanup call is deliberately narrow: it does not solve the problem again, but rewrites the selected answer into exactly one \texttt{\textbackslash boxed\{\}} expression. This design improves accuracy when at least one candidate avoids the dominant single-chain error and the selector can identify the better-supported answer.

\paragraph{HumanEval workflow.} HumanEval exposes an additional signal that math problems do not: code can be executed against public tests. The HumanEval \texttt{manual\_v1} workflow first generates two independent implementations. Each candidate is tested when public tests are available. If a candidate fails, a reflection step receives the failing test feedback and edits the code instead of starting from scratch. The workflow prefers a candidate that passes public tests. If no tested candidate passes, it falls back to ensemble-style selection among repaired candidates. This design improves over direct prompting because execution feedback catches local defects that are hard to spot from text alone, while candidate diversity reduces the chance that both attempts share the same implementation error.

\paragraph{Ablations.} The MATH single-candidate ablation removes candidate diversity while keeping the final formatting cleanup. The HumanEval no-public-test ablation removes execution-feedback repair while increasing candidate diversity. These ablations separate two possible sources of improvement: better search over multiple candidates and explicit feedback from tests.

The design choice for MATH is to spend calls on independent reasoning paths because symbolic mistakes often arise from early false assumptions. The final cleanup call is intentionally narrow: it does not solve the problem again, but makes the selected answer compatible with the benchmark extractor. The HumanEval design instead prioritizes executable feedback, because public tests can identify syntax, entry-point, and simple semantic errors before final scoring. The no-public-test ablation is retained because its full-test result shows that extra candidate diversity can outperform the execution-feedback variant for this model, albeit at higher token cost.

On MATH, CoT improves over direct prompting from 0.90 to 0.95. The full \texttt{manual\_v1} workflow reaches 1.00, while the single-candidate ablation remains at 0.90. The no-public-test ablation is especially costly because it generates and selects among candidates without early execution-feedback filtering.

Failure analysis found MATH evaluator false negatives caused by text-answer formatting such as \texttt{MAKE} versus \texttt{\textbackslash text\{MAKE\}}, comma spacing inside text answers, percent signs, variable-assignment prefixes, nested boxed expressions, and reference solutions that express multi-answer outputs as multiple \texttt{\textbackslash boxed\{\}} values. The evaluator now normalizes simple text wrappers, compares comma-separated answer lists as unordered lists, preserves grouped tuple answers, and combines multiple boxed reference answers before symbolic comparison. Remaining MATH baseline failures include genuine reasoning/counting issues, such as the rectangle-counting problem solved by \texttt{manual\_v1} but missed by CoT.

To check whether the MATH gain persists beyond the 20-sample subset, Table~\ref{tab:math50} reports a 50-sample validation run with the same seed. On this larger subset, \texttt{manual\_v1} remains above direct prompting, CoT, and the single-candidate ablation, but it uses about nine times as many tokens as direct prompting. A rescored failure analysis shows that \texttt{manual\_v1} fixes two of the three CoT failures with no CoT-relative regressions: the rectangle-counting problem at index 15 and the elevator probability problem at index 100. Its only remaining failure is the arc-length problem at index 91, which every compared method misses. The extracted answer is consistently \(\frac{17\sqrt{10}}{2}\) while the reference is \(\frac{25\sqrt{10}}{4}\), so this remaining error is a reasoning failure rather than a local rescoring issue. The single-candidate ablation fixes one CoT failure but introduces one regression, supporting the value of multi-candidate generation plus selection.

\section{Observations and Reflections}

My first observation is that candidate diversity is more useful than simply asking for longer reasoning. On the full MATH test split, CoT only improves direct prompting by 0.00411, while \texttt{manual\_v1} improves it by 0.02881. The important difference is not just that \texttt{manual\_v1} spends more tokens, but that the extra tokens are spent on independent reasoning paths. This gives the workflow a chance to recover when one path makes an early false assumption. The 50-sample failure analysis supports this: \texttt{manual\_v1} fixes CoT failures on rectangle counting and probability problems without introducing CoT-relative regressions on that subset.

My second observation is that execution feedback helps HumanEval, but it is not the only source of improvement. The \texttt{manual\_v1} HumanEval workflow improves over direct prompting by using public tests and repair. However, the no-public-test ablation scores even higher in the tracked full test. I interpret this as evidence that public tests are useful but incomplete: they catch obvious local bugs, yet they may not cover enough behavior to dominate the benefit of sampling more diverse implementations. For code tasks, the best workflow may therefore need both stronger test generation and candidate diversity, rather than relying only on the provided public tests.

My third observation is that evaluation format matters for agent workflows. Several MATH failures were not model failures at first, but extraction or normalization mismatches such as text answers, percent signs, nested boxed expressions, or multiple boxed reference answers. This matters because a workflow can generate a correct mathematical answer and still lose credit if the final answer is not canonicalized. The final cleanup step in the MATH workflow is therefore not cosmetic; it protects the answer selected by the workflow from avoidable formatting errors.

Finally, the experiments make the accuracy--cost tradeoff explicit. The MATH workflow improves the full-test score, but it costs about five times as many calls and almost nine times as many tokens as direct prompting. My view is that multi-agent workflows should be adaptive: use direct or CoT for easy problems, trigger candidate diversity only when uncertainty is high, and reserve expensive selection or verification calls for cases where the expected accuracy gain justifies the cost.

\section{Optional Follow-up Experiments}

The required experiment set is complete. Optional follow-up experiments would mainly test whether the MATH accuracy gain can be retained at lower cost:

\begin{enumerate}
    \item Use the 50-sample MATH failure analysis to decide whether the shared arc-length failure can be addressed without increasing the already high token budget.
    \item Tune MATH prompts or add verification only on validation data if a low-cost fix is clear.
    \item Add larger MATH ablations on the full test split: remove ensemble, reduce candidate count, and compare non-thinking against thinking-enabled Kimi K2.5.
\end{enumerate}

\section{Limitations}

The manual workflows increase token usage and latency, especially for MATH. The full MATH \texttt{manual\_v1} run improves accuracy but uses 2,431 calls and 3,786,936 tracked tokens, which is 5.00 times the direct baseline calls and 8.91 times the direct baseline tokens. Using the Kimi K2.5 price schedule checked on 2026-06-01, the full MATH \texttt{manual\_v1} workflow alone is estimated at CNY 38.73--45.36, and the recorded required API subtotal is estimated at CNY 73.15--82.43. The main limitation is therefore not whether multi-agent decomposition can improve accuracy, but whether the improvement is worth the extra calls for a given deployment budget.

\section{Conclusion}

The experiments show that task-specific multi-agent workflow design can improve over direct and CoT prompting when the extra calls target concrete failure modes. On MATH, independent reasoning candidates plus answer selection improve the full-test score to 0.91770, above both direct prompting and CoT. On HumanEval, candidate generation and execution-aware repair improve over direct prompting, while the no-public-test ablation shows that candidate diversity itself is also a strong contributor. The cost analysis shows the tradeoff clearly: the proposed MATH workflow is more accurate, but much more expensive. Future work should therefore focus on cheaper selectors, adaptive candidate counts, and verification calls only for examples that appear uncertain.
